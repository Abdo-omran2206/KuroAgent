## 20. Production Packaging, EXE Architecture & Self-Modification

Kuro is a long-term autonomous AI agent, so its Windows packaging architecture must support modularity, plugins, skills, persistent memory, and safe self-improvement.

### 20.1 PyInstaller Strategy

DO NOT use PyInstaller `--onefile` as the primary production architecture.

Use:

```bash
pyinstaller --onedir
```

The final application should be a directory-based application.

Example:

```text
Kuro/
├── Kuro.exe
├── _internal/
├── core/
├── tools/
├── plugins/
├── skills/
└── ...
```

The user should receive a single installer such as:

```text
KuroSetup.exe
```

but the installed application itself should remain modular/multi-file.

### 20.2 Separate Application Files from User Data

Never allow Kuro to directly modify its installed files inside:

```text
C:\Program Files\Kuro\
```

Treat the installed application/core as mostly immutable.

Use a structure similar to:

```text
C:\Program Files\Kuro\
├── Kuro.exe
├── core/
├── tools/
├── runtime/
└── resources/
```

User-writable data should live separately:

```text
%APPDATA%\Kuro\
├── brain/
├── memory/
├── skills/
├── plugins/
├── config/
├── logs/
├── cache/
├── projects/
└── updates/
```

Do not hard-code absolute paths.

Create a centralized path/configuration manager that handles:

* Application directory
* User data directory
* Config directory
* Memory directory
* Plugin directory
* Skill directory
* Logs directory
* Cache directory
* Temporary/update directory

The application must work correctly regardless of where it is installed.

### 20.3 Plugin and Skill Based Extensibility

Kuro should be able to extend itself without modifying its core executable.

Implement:

```text
%APPDATA%\Kuro\plugins\
%APPDATA%\Kuro\skills\
```

New capabilities should preferably be installed as:

* Plugins
* Skills
* Custom tools
* Tool configurations
* Prompt/configuration extensions

rather than modifying the core source.

The architecture should allow Kuro to discover and load these dynamically.

Implement proper:

* Plugin manifest
* Versioning
* Dependency declaration
* Enable/disable state
* Validation
* Loading errors
* Plugin isolation where practical

Example:

```text
plugins/
└── github/
    ├── plugin.json
    ├── plugin.py
    └── README.md
```

### 20.4 Safe Self-Modification

Kuro must NOT modify the currently running executable or overwrite its own active installation directly.

If Kuro decides that a core change is necessary, use a staged process:

```text
Current Version
      ↓
Git Checkpoint
      ↓
Create Isolated/Staging Copy
      ↓
Apply Changes
      ↓
Run Static Checks
      ↓
Run Tests
      ↓
Build New Version
      ↓
Run Validation
      ↓
Promote New Version
      ↓
Rollback if Anything Fails
```

The running Kuro process must remain untouched until the replacement has been successfully validated.

### 20.5 Versioned Self-Update System

Implement a version-aware update mechanism.

Example:

The system should support:

* Current version

Never delete the previous working version until the new version has successfully passed validation.

```text
Provides authentication + service connection

Tool
    ↓
Provides an executable capability

Agent
    ↓
Chooses the appropriate tool
```

Example:

```text
GitHub Integration
       │
       ├── github_search_repo
       ├── github_read_file
       ├── github_create_issue
       └── github_create_pr
```

This allows Kuro's ReAct agent to discover and use integration capabilities like any other tool.

### 21.15 External Event System

Design the integration layer so it can eventually receive external events.

Examples:

```text
GitHub
 ↓
New Issue
 ↓
Kuro Event

Email
 ↓
New Important Email
 ↓
Kuro Event

Calendar
 ↓
Upcoming Meeting
 ↓
Kuro Event
```

This can later connect to Kuro's:

* Task State Machine
* Memory
* Notifications
* Planner
* Automation system

### 21.16 Webhooks and Polling

Where supported, use webhooks/event subscriptions.

Otherwise support controlled polling.

Do NOT implement aggressive continuous polling.

The architecture should support:

```text
Webhook
OR
Scheduled Polling
OR
Manual Check
```

### 21.17 Custom Integration SDK

The architecture should allow developers/users to create their own integrations.

Example:

```text
integrations/
└── my_service/
    ├── integration.json
    ├── integration.py
    ├── tools.py
    └── README.md
```

Provide documentation for creating custom integrations.

A future developer should be able to add a new service without modifying the Kuro core.

### 21.18 Integration Marketplace — Future Architecture

Do not implement a marketplace now unless necessary.

However, design the integration/plugin system so that a future marketplace could distribute:

```text
Plugins
Skills
Integrations
Tools
Agents
Templates
```

Each package should support:

* Name
* Version
* Author
* Description
* Dependencies
* Required permissions
* Compatibility version
* Installation metadata

### 21.19 Safety Principle

Kuro is allowed to read information automatically when the user has authorized the integration.

Actions that create external side effects should have explicit permission boundaries.

Examples:

```text
Read email
→ Usually safe

Summarize email
→ Safe

Draft email
→ Usually safe

Send email
→ Confirmation by default

Read GitHub repository
→ Usually safe

Create GitHub issue
→ Confirmation by default

Delete GitHub repository
→ Strong confirmation / restricted

Read Drive file
→ Usually safe

Delete Drive file
→ Confirmation required
```

The permission system must remain centralized rather than being independently implemented by every integration.

### 21.20 Implementation Requirement

Before implementing integrations:

1. Inspect the existing Kuro architecture.
2. Inspect the existing tool registry.
3. Inspect the permission/security system.
4. Inspect configuration handling.
5. Inspect memory architecture.
6. Inspect the existing web/API capabilities.
7. Design the Integration Manager around the existing architecture.
8. Avoid duplicating existing functionality.
9. Implement one integration end-to-end first.
10. Generalize the architecture only after the first integration works correctly.
11. Add tests for authentication, permissions, errors, token expiration, and disconnected accounts.
12. Preserve backward compatibility.

Do NOT rewrite Kuro from scratch.

The final architecture should make Kuro capable of operating across:

```text
Local Computer
      │
      ├── Files
      ├── Terminal
      ├── Browser
      ├── Applications
      │
      ▼
External Services
      │
      ├── GitHub
      ├── Google Drive
      ├── Email
      ├── Calendar
      ├── Discord
      ├── Telegram
      ├── Notion
      └── Custom APIs
```

Kuro should treat both local capabilities and external integrations as part of one unified capability system.
